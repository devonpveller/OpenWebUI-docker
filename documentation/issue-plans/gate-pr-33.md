## Reasoning

**The fatal defect — verified against the base tree, not inferred.** The script polls `http://localhost:8080/observe/queue` (`queue-eta-notify.ps1:56`, used in `Get-QueueSnapshot`). At base `a1322f5`, `observe.py`'s `/observe/queue` delegates to `control.get_queue`, which returns:

```python
{"models": {name: mq.snapshot() for ...}, "held_total": ..., "max_total_connections": ...}
```

— i.e. the per-model `snapshot()` dict the worker built everything around sits **one level down, keyed by model name**, alongside two extra top-level fields. `Get-FlaggedLanes` reads `$Snapshot.model`, `$Snapshot.avg_T_s`, and `$Snapshot.waiting` at the **top level**. On the live payload those properties don't exist, so `$waiting = @()`, zero lanes flag, and every pass logs "queue idle or nothing over the threshold" — forever, silently, while research jobs sit queued. The feature ships as dead code that reports success.

**Why the tests are green anyway.** Both fixtures replicate `ModelQueue.snapshot()` (`scheduler.py`, the `snapshot()` method) — the PR description even cites it as proof of correctness ("full `snapshot()` shape (matches `llm-queue/src/llm_queue/scheduler.py:272-303`)"). That claim is true and is precisely the trap: the fixtures match the *internal helper*, not the *route*. Every python assert, the threshold math, and the `-SnapshotFile` dry-runs all exercise the wrong contract, so the worker's entire evidence chain passes while the deliverable fails the issue intent. Compounding this, the real board is multi-model (the registry serves both chat and embed lanes — `control.get_queue` iterates `queues().items()`), so the flat shape can't even represent real data; a correct implementation must iterate `models.*`.

**Root cause is upstream of the worker.** The gate-plan itself specified the fixture as "matching `snapshot()` in `llm-queue/src/llm_queue/scheduler.py:272-303`" and described `/observe/queue` by citing scheduler lines. The worker reproduced the plan faithfully. This is a planning-contract error, not worker dishonesty — the worker's explicit "Not verified in sandbox" section shows the evidence-assignment discipline held.

**Secondary defect (PLAUSIBLE — statically grounded, not executed here).** The dedup state round-trips through PS 5.1 `ConvertTo-Json`, which serializes `DateTime` as `"\/Date(ms)\/"` (JavaScriptSerializer). Pass 1 saves an ISO string (`Invoke-QueueEtaCheck`: `(Get-Date).ToUniversalTime().ToString("o")`); pass 2 loads it via `[DateTime]::Parse` (`Get-DedupState`) and then unconditionally re-saves the now-`DateTime` values (`Save-DedupState`), producing `\/Date()\/` in the file — already violating the runbook's documented ISO-8601 state schema. On pass 3, `ConvertFrom-Json` yields a UTC-kind `DateTime`; `[DateTime]::Parse` on it coerces through a kind-less string, shifting the instant by the host's UTC offset (or, if coercion throws, the silent `catch { }` drops the lane entirely). Either way the 10-minute cooldown breaks by the third poll on any non-UTC host — duplicate Mattermost pings roughly every 2 polls for a long-held lane, the exact spam the feature promises to prevent. The plan's logic tier ("a re-run emits nothing") only checks 2 passes, so this would have slipped through even the host tier as written.

**Noted, not deciding:** `install-service` inherits the watchdog's `sc.exe create` + `powershell.exe` binPath pattern (`stack-watchdog.ps1:1518,1530`), which cannot satisfy the SCM handshake (error 1053), and `$MyInvocation.MyCommand.Path` inside the function resolves empty in PS 5.1 — yet the runbook's primary silencing advice is `Stop-Service QueueEtaNotifier`. Mirroring was mandated, so this doesn't count against the worker, but the runbook documents an operational path that can't exist.
