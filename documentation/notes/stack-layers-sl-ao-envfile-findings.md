## 1. The measured variable set

**The question.** `ao-worker-1` and `ao-worker-2` carried
`env_file: ../../.env`. Replacing it means naming every variable the
`little-coder:local` image reads that the wildcard was carrying and the
services' own `environment:` block was not already setting. Too few names and
the pool breaks on its next recreate; too many and the grant is back under
another spelling.

**The method**, three sets intersected:

```
A = every variable the image reads CONTAINER-side
  = the literal os.environ / getenv reads under little-coder/src/littlecoder/**
    and little-coder/pi-extension/**
  + the INDIRECT reads, where the config names the variable and the code reads
    that name (config.py inference.api_key_env, workspace.open_terminal_key_env)
B = the PRE-SPLIT root .env.example: 157 assignments, 153 UNIQUE names (four
    are assigned twice: LC_LLAMA_API_KEY and three GPU_*_DEVICE_ID)
  = git show 4934529:.env.example | grep -E "^[A-Za-z_][A-Za-z0-9_]*=" | cut -d= -f1 | sort -u
C = what the workers' own environment: block already sets (ten names)

added = (A INTERSECT B) MINUS C
```

`A INTERSECT B` is four names. Two were already in `C`:

| name | in `A` because | in `C`? |
|---|---|---|
| `LC_ROUTE_EXEC` | `little-coder/pi-extension/open-terminal-exec/index.ts` and its README gate the extension on it | YES — `LC_ROUTE_EXEC=1` |
| `OPEN_TERMINAL_API_KEY` | INDIRECT: `little-coder/src/littlecoder/config.py:91` `open_terminal_key_env` default, read at `daemon.py:183` and `agent.py:265` | YES — `OPEN_TERMINAL_API_KEY=${AO_OPEN_TERMINAL_KEY}` |
| **`LC_DEPLOY_TOKEN`** | `little-coder/src/littlecoder/daemon.py:520` and `:554`, both `req.token or os.environ.get("LC_DEPLOY_TOKEN") or None` — the global fallback on the clone/deploy path | **NO** |
| **`LC_LLAMA_API_KEY`** | INDIRECT: `little-coder/src/littlecoder/config.py:38` `api_key_env: str = "LC_LLAMA_API_KEY"`, read at `meta_wiring.py:42` and `:48` (embedding client and chat client) and `agent.py:271` | **NO** |

So exactly two names were added:
`agent-org/docker/docker-compose.yml:389-390` (ao-worker-1) and `:482-483`
(ao-worker-2) — search for `LC_DEPLOY_TOKEN=${LC_DEPLOY_TOKEN}`.

**The indirection is the whole trap.** The workers already set
`LLAMACPP_API_KEY=${LC_LLAMA_API_KEY}` (`:369`, `:474`). That is a HOST-side
interpolation injecting a DIFFERENTLY-NAMED container variable, which `pi`
reads. little-coder itself reads the name `LC_LLAMA_API_KEY`, and until this
change the wildcard was its only route in. An enumeration of literal
`os.environ("…")` strings alone misses it, which is how the earlier pass missed
it (sl-env-split findings §14, X-F10).

The workers run `agent-org/agent-bridge/worker-configs/worker-N/`, generated by
`agent-org/scripts/gen-worker-configs.py` from
`little-coder/config/little-coder.config.yaml`, whose `:12` is
`api_key_env: LC_LLAMA_API_KEY` and `:66` `open_terminal_key_env:
OPEN_TERMINAL_API_KEY` — so the defaults in `config.py` are what the pool
actually runs with. (The generated directory is not in git; the generator and
the canonical config are.)

**Ruled out, with the reason:** `LITTLE_CODER_VERSION` is in `B` and looks like
a worker variable. It is a build ARG only —
`little-coder/docker/Dockerfile.agent:36-37`, `ARG LITTLE_CODER_VERSION=1.10.0`
consumed by the `npm install -g` line. The workers run the prebuilt image, so
its presence or absence in a container's environment changes nothing. Read the
Dockerfile rather than assuming.

**Cross-check against the LIVE root file, not just the example.** The live root
`.env` on this host carries 23 assignments (names only, no values read out of
it). Intersecting those 23 names against the same source sweep yields **zero**.
The one that looks like a worker variable, `LC_POLYSHDESIGN_TOKEN`, is read by
the BRIDGE — `agent-org/agent-bridge/app/modules/projects.py` `owner_token_env`,
resolved in `orchestrator.py` `_project_token` — out of agent-org's own `.env`,
where `.env.example` already declares it. So nothing else the root file still
holds is a name the pool would miss.

**Nothing was added that nothing reads.** That is the second half of the
acceptance, and it is the half that is easy to fail by being generous.

## 2. What the renders proved

Two short-path scratch clones, `git -c core.longpaths=true clone`, one at the
branch tip and one at `bdcc7f1`, each seeded with
`cp agent-org/docker/.env.example agent-org/docker/.env`, stdout and stderr
captured separately.

**The strongest single result came before the diff.** On `bdcc7f1`, in a clone
with no root `.env` — which is what a fresh checkout is —

```
docker compose -f agent-org/docker/docker-compose.yml --profile workers config
  exit 1
  env file D:\wtenv\b\.env not found: GetFileAttributesEx ...
  + 4x  The "LC_LLAMA_API_KEY" variable is not set. Defaulting to a blank string.
```

The branch tip renders **exit 0 with no root `.env` present at all**. The plane
is now self-contained.

To get a comparable render out of `bdcc7f1` I seeded its root `.env` from its
own `.env.example` (three names). Normalized diff (repo path prefix folded),
`--profile workers`, development -> branch, in full:

| service | change |
|---|---|
| `ao-worker-1`, `ao-worker-2` | **+** `LC_DEPLOY_TOKEN: ""`, **+** `LC_LLAMA_API_KEY: llama` |
| `ao-worker-1`, `ao-worker-2` | **-** `NAS_BACKUP_USER`, **-** `NAS_BACKUP_PASSWORD`, **-** `TEST_VALIDATION_LLM_KEY` |
| `ao-worker-1`, `ao-worker-2` | `LLAMACPP_API_KEY: ""` -> `llama` |
| `ao-ot-1`, `ao-ot-2` | `LLAMACPP_API_KEY: ""` -> `llama` |
| `agent-bridge` | **+** `LC_DEPLOY_TOKEN: ""`, **+** `LC_LLAMA_API_KEY: llama` |
| everything else | byte-identical |

Four of those five rows want a sentence each, because only the first is the
change itself:

* The three REMOVALS are the blast radius made visible. With the root `.env`
  trimmed to three names, those three names are what the wildcard was still
  delivering — the NAS backup credentials and the T2 validation key, into two
  agent containers that read none of them. Before the trim it was 151: of the
  153 unique names the pre-split example carried, exactly two
  (`LC_ROUTE_EXEC`, `OPEN_TERMINAL_API_KEY`) were overridden by the workers'
  own block, so 151 arrived unopposed. The inherited "151" in the runbook and
  in sl-env-split findings §14 is therefore CORRECT - re-derived here rather
  than copied.
* `LLAMACPP_API_KEY` changing from `""` to `llama` on FOUR services is not a
  compose-file change at all: it is `agent-org/docker/.env.example` gaining
  `LC_LLAMA_API_KEY`, which those four services already interpolated. It is the
  same edit that removes the four `variable is not set` warnings.
* `agent-bridge` gains both names because it has `env_file: - .env` at
  `agent-org/docker/docker-compose.yml:165-166` — agent-org's OWN file, which
  is legal by construction and stays. **Any** variable added to a plane's env
  file reaches every service that names that file; there is no way to declare a
  value for compose interpolation without it. It reads neither name (both appear
  in `agent-bridge/app/` only in docstrings, describing "the pool's ambient
  `LC_DEPLOY_TOKEN`"), and on the LIVE host it already receives both, because
  sl-env-split copied them into `agent-org/docker/.env` by hand on 2026-09-19.
  So this row is a fresh-clone artifact, not a change in what the bridge gets.

`--profile workers --profile cloud`: same rows, plus the cloud services
unchanged. Bare (no profile): the only row is `agent-bridge`'s two additions —
and note that development emits the four `LC_LLAMA_API_KEY` warnings even on a
BARE render, because compose interpolates the whole file regardless of which
profiles are selected.

## 3. The check: what it did before, and what it does now

`scripts/checks/check-env-file-scope.ps1` exists to stop exactly this grant. It
did not stop it, and the reason is not the regex — `Test-BroadTarget` matched
`../../.env` correctly, and `-All` printed both grants in red every time it was
run from the main checkout.

**It was the debt clause.** In staged mode the script re-scanned `HEAD:<path>`
and dropped from the violation list any target already present there, printing
`(pre-existing, not blocked)`. Measured, in a clone at `bdcc7f1` with agent-org's
compose file staged:

```
OLD script:  (pre-existing, not blocked) agent-org/docker/docker-compose.yml:352
             (pre-existing, not blocked) agent-org/docker/docker-compose.yml:444
             env_file scope: no new shared-.env grants staged.     exit 0
NEW script:  env_file grant of a shared .env in a staged compose file (2):
               ...:352: env_file -> ../../.env -- is the repo root env file
               ...:444: env_file -> ../../.env -- is the repo root env file
                                                                    exit 1
```

That is the whole answer to "why do they pass today": every commit touching
agent-org's compose file got a green line about grants the audit mode called
violations. The clause had a real rationale (a guard that blocks unrelated
commits over pre-existing debt gets disabled, and then guards nothing) and it
outlived it the moment the debt was paid. **There was no named exemption and no
service list — the grandfathering WAS the exemption, applied automatically and
invisibly to whatever was already in the tree.**

**After.** The verdict is a resolution, not a substring. The target is resolved
against the directory of the compose file naming it:

| resolves to | verdict | proved by |
|---|---|---|
| the repo root `.env` | REFUSED | planted `- ../../.env` on `ao-ot-1`: staged exit 1, `-All` exit 1 |
| the compose file's own directory | ALLOWED | agent-bridge's `- .env` never flagged in any run |
| a parent directory that is not the root | ALLOWED | planted `- ../.env` in `inference/compose/upstreams.yml` (= `inference/.env`): exit 0 |
| another directory (cross-plane) | REFUSED | planted `- ../../coder/.env` there: `belongs to another directory (coder)`, exit 1 |
| outside the repo, or absolute | REFUSED | by construction in `Resolve-RepoRelative` |

Unplanting returns both modes to exit 0 on the branch tip.

### 3a. `-All` was blind inside a worktree

Separate defect, found while trying to run the audit from this worktree. The
prune matched the **absolute** path against `[\\/](\.git|\.claude|node_modules|OB1)[\\/]`.
An agent worktree lives under `<repo>\.claude\worktrees\<id>\`, so every file in
the tree it was asked to audit matched the `.claude` clause and was skipped.
Measured before the fix:

```
-All (cwd = worktree)                  -> "clean - no service grants itself a shared .env."  exit 0
-All -Root "D:\Open WebUI\ai-stack"    -> 2 violations                                        exit 1
```

Same commit, same two grants, opposite verdicts. The prune now matches the path
RELATIVE to the scan root, so a worktree audits itself and the main checkout
still skips `.claude/worktrees`.

### 3b. The four files that define the inference plane were not in the file set

Found while proving the "a plane's own `../.env` is allowed" row of the table
above: I planted one in `inference/compose/upstreams.yml`, staged it, and the
check said `no compose files staged - skipped`. Both modes selected files by
basename — `compose*.yml` / `docker-compose*.yml` — and the inference plane's
2026-09 split named its four fragments `backups.yml`, `gateway.yml`,
`queue.yml`, `upstreams.yml`. Those files declare real services with real
`environment:` blocks, and a grant in any of them was invisible in both modes.

Now scanned: any `.yml`/`.yaml` whose immediate directory is named `compose`,
plus `*.override.yml` (which picks up `portal/local-test.override.yml`).
`.gitattributes` already carries a `*/compose/*.yml` rule for the same plane
split, so this is the repo's own convention. `-All` still exits 0 after the
widening, so it added no violations; planting `- ../../.env` in
`inference/compose/upstreams.yml` now goes red in both modes.

**Still blind:** a `.yml` that is neither named `compose*` nor sits in a
`compose/` directory nor ends `.override.yml`. Recording that rather than
scanning every YAML in the tree.

### 3c. The regression attempt 1 shipped: the verdict resolved a token that was not a path

Found by the tester, not by me, and it is the defect that failed the attempt.
The resolving verdict in 3's table took the RAW token and split it on `/`. For
the two value shapes where the token is not bare path text, the unparsed leading
fragment was swallowed as an ordinary path SEGMENT and the following `..` popped
it, so the target resolved to the compose file's OWN directory and was ALLOWED:

| shape | what the old parser saw | verdict |
|---|---|---|
| `env_file: [../../.env]` | segments `[..`, `..`, `.env` | allowed (wrong) |
| `- path: ../../.env` + `required: false` | segments `path: ..`, `..`, `.env` | allowed (wrong) |

Both are real grants. Rendered on `ao-ot-1` with a root `.env` present, docker
injected `NAS_BACKUP_USER` and `TEST_VALIDATION_LLM_KEY` into a container that
had neither - re-measured here, `render exit 0 | leaked lines: 2` for each.
And it was a REGRESSION, not an inherited hole: `bdcc7f1`'s `Test-BroadTarget`
matched `\.\.[\\/]` against the raw text and went red on both.

**The lesson is the shape of the mistake, not the two shapes.** Replacing a
substring test with a semantic one buys precision and pays for it in a
dependency the substring test did not have: the semantic test must PARSE. I
added the parse's consumer and not the parse. So the fix is not two more cases -
it is reading the value into paths first and REFUSING what will not read:

* `Remove-YamlComment` (quote-aware), `Remove-Quotes`, `Get-EntryPath` (scalar,
  `path:` long form, `{path: ..., required: ...}` flow mapping, `required:`/
  `format:` entries which name no file), `Get-InlineValueEntries` (scalar or
  flow sequence, one entry each so a two-item sequence reports the bad ITEM).
* A `path:` key on a CONTINUATION line keeps the block sequence open, so
  `- required: false` / `  path: ../../.env` is caught; so does a blank line.
* Plain-path-text guard: a residual `[`, `]`, `{`, `}`, `,`, whitespace or `$`
  means the value did not parse or its target is not knowable from the file.
  REFUSED, printed, not normalized.
* Fail-closed backstop for the shapes nobody has thought of yet: a value whose
  raw text climbs with `..` and whose resolution lands back inside the compose
  file's own directory is refused, because that is what a lost fragment looks
  like. It also refuses `../<thisdir>/.env`, which should be written `.env`.

**Proof, 37 planted shapes, each staged and run through the check alone** (27 on
`ao-ot-1` in agent-org's compose, 10 on `llama-cpp-upstream` in
`inference/compose/upstreams.yml`, which sits one level BELOW its plane so
`../.env` is the plane's own file and `../../.env` is the root - the pair the
resolution has to tell apart in every shape). RED: scalar, quoted scalar,
scalar with trailing comment, flow sequence, quoted flow sequence, two-item flow
sequence with one bad item, unterminated flow sequence, block item, quoted block
item with comment, `./`-prefixed, long-form `path:`, quoted long-form,
`required:`-first with `path:` on the next line, long-form flow mapping,
`../../../.env`, an absolute `D:/x/.env`, `../../.env.test`, `../../coder/.env`,
`${SOME_ENV_FILE}`, a blank line mid-list then a bad item, all five root shapes
from the `compose/` fragment, and `../docker/.env` - which resolves somewhere
LEGAL and is refused anyway, by the backstop, because climbing and landing back
home is what a mis-parsed value looks like. GREEN: `.env`, quoted `.env` with
comment, `./.env`, `[.env]`, long-form `path: .env`, `../.env` from agent-org's
own compose file (= `agent-org/.env`, a parent that is not the root), and all
four plane-own `../.env` shapes from the fragment. Mismatches: 0.

Two process notes, because both cost me a wrong measurement in this round:
`git checkout -- <path>` after a `git add` restores from the INDEX, so it
restores the PLANT - `git checkout HEAD -- <path>` is the one that unplants; and
a matrix run against a scratch clone proves nothing unless the script under test
was copied in AFTER the last edit. I read one green matrix off a clone holding
the attempt-1 script before noticing.
