# Personal Memory Stack — Three-Layer Setup (v2)

> **For Claude Code:** This document is a project spec. Read it end-to-end before taking any action. Treat the "Tasks" section as the work list. Before installing or modifying anything, summarize back to me what you're about to do and wait for confirmation. Do not run destructive commands without explicit approval.

> **What changed from v1:** Open Notebook has been removed from the architecture. Its responsibilities (external-document ingest, synthesis, browsable wiki view) are absorbed into OpenBrain plus a compiled wiki layer. The stack is now mnemory + OpenBrain + compiled wiki, with OpenBrain as the single source of truth for everything that isn't agent-extracted user facts.

## What we're building

A three-layer personal knowledge stack where each layer owns a distinct role and the agent can route queries unambiguously. The wiki is a generated artifact, not an editable system — it is downstream of OpenBrain, and is rebuilt by a scheduled compiler that reads from OpenBrain's structured data.

The three layers:

1. **mnemory** — agent-facing semantic memory. Stores short extracted facts _about the user_ (preferences, decisions, identity, working context). Auto-extracts from conversations. Repo: `https://github.com/fpytloun/mnemory`.

2. **OpenBrain (OB1)** — single source of truth for everything that isn't a user-fact. Holds structured records (contacts, calendar, captured thoughts, projects) **and** external source documents ingested as structured rows (papers, articles, podcast transcripts, web pages). Supabase + pgvector. Repo: `https://github.com/NateBJones-Projects/OB1`.

3. **Compiled wiki** — read-only synthesis artifact. Generated by a scheduled compiler agent that reads from OpenBrain, builds a knowledge graph, and writes wikilinked markdown plus a graph manifest. Browsable in Obsidian, served read-only via a web viewer for mobile/cross-device access. Never edited directly; if a page is wrong, fix the OpenBrain row and recompile.

The wiki is the only one of these three artifacts that gets rebuilt on a schedule. mnemory and OpenBrain are live and incremental. The wiki is a snapshot — always rebuildable, always disposable.

## Source-of-truth rules

These are absolute. Build the tool configs and the routing skill around them.

| Concern                                                   | Owner                     | Other layers must                                                 |
| --------------------------------------------------------- | ------------------------- | ----------------------------------------------------------------- |
| Facts about the user as a person                          | mnemory                   | Never create "about me" pages or rows                             |
| Domain records (contacts, calendar, thoughts, projects)   | OpenBrain                 | Never duplicate as memory facts                                   |
| External source documents (papers, articles, transcripts) | OpenBrain (sources table) | Never store source content elsewhere                              |
| Synthesized knowledge across sources                      | Compiled wiki (output)    | Never treated as canonical — fix OpenBrain and recompile if wrong |

The wiki is **never authoritative**. If the wiki contradicts OpenBrain, OpenBrain wins. If the wiki has an error, you fix the underlying source row and trigger a recompile. This is the entire point of the architecture: it prevents the "wiki drift" failure mode where AI-generated synthesis becomes the trusted artifact and quietly diverges from reality.

## Routing rules (for the agent)

These get written into the system prompt or a Claude Code skill. Verbatim:

```
You have access to three knowledge tools. Route as follows:

- Questions about the user as a person — preferences, decisions, identity,
  working style, recent context — go to `mnemory`.

- Questions that look up specific records — a contact, a calendar event,
  a captured thought, a project, a specific source document — go to
  `openbrain`.

- Questions about synthesis or topic-level understanding — what the
  literature says about X, how multiple sources relate, the current
  state of thinking on a subject — go to `wiki`. Prefer compiled wiki
  pages over raw source retrieval. If the wiki is insufficient, fall
  back to openbrain's source rows.

For ambiguous questions, ask once which lane the user means before
searching. Never query more than two layers in a single turn unless
the user explicitly asks for a cross-layer answer.

If the wiki and openbrain disagree, openbrain is authoritative. Flag
the discrepancy to the user.
```

### Task 4 — Extend OpenBrain for URL/document ingest

OB1's base schema is centered on `thoughts`. For our architecture, OpenBrain also needs to hold external sources. Add a `sources` table (or use an existing extension if one exists; check the `recipes/` and `extensions/` directories first).

The `sources` table needs at minimum:

- `id` (uuid)
- `url` (text, nullable — sources may be uploaded files, not URLs)
- `title` (text)
- `content` (text — the extracted body)
- `content_type` (enum: web_article, pdf, youtube_transcript, podcast_transcript, paper, manual)
- `tags` (text array)
- `notebook` or `project` (text, nullable — for grouping)
- `fetched_at` (timestamp)
- `embedding` (vector, for semantic search via pgvector)
- `metadata` (jsonb — author, date, source-specific fields)

Build an MCP tool `openbrain_ingest_url(url, notebook?, tags?)` that:

1. Fetches the URL using Firecrawl, Jina Reader, or Playwright depending on content type
2. Extracts text + metadata
3. Embeds the content
4. Writes a `sources` row
5. Returns the row ID

For YouTube URLs, use the YouTube transcript API. For PDFs, use a PDF text extractor. The fetching layer should be modular so additional content types can be added later.

Also add `openbrain_ingest_urls(urls[], notebook?)` for batch ingest — accepts a list of URLs and processes them in parallel.

### Task 8 — Smoke tests

Once everything is wired, run these end-to-end:

1. **mnemory:** In Claude Desktop or Claude Code, say "Remember that I prefer Python over JavaScript for new projects." Confirm it shows up in mnemory's management UI.
2. **OpenBrain (records):** Capture a thought via the MCP. Ask the agent to retrieve it. Confirm it comes back through `openbrain`.
3. **OpenBrain (source ingest):** Ingest a URL via `openbrain_ingest_url`. Ask the agent a factual question whose answer is in that source. Confirm it comes back through `openbrain`.
4. **Wiki:** After the compiler runs, ask the agent a topic-level synthesis question. Confirm the answer comes from `wiki` and references compiled pages.

If any smoke test fails, report which one and stop.

## Constraints — read before doing anything

- **Do not install or modify anything system-wide without confirming first.** Use Docker containers, virtual environments, and per-project directories. No `sudo apt install`, no global `npm install -g`, no modifying shell rc files without showing the diff first.
- **Do not commit secrets.** API keys go in `.env` files that are in `.gitignore`. If a repo doesn't have `.gitignore` covering it, add it.
- **Do not auto-share or push anything.** All repos stay local until the user explicitly asks to push.
- **Do not run destructive commands** without explicit confirmation in chat.
- **The wiki is never authoritative.** If you find yourself "fixing" wiki content directly, stop. Fix the OpenBrain source row instead and trigger a recompile.
- **Be wary of overlap creep.** If at any point you find yourself creating "memory" features in OpenBrain, "source storage" outside OpenBrain, or treating the wiki as editable, stop and re-read the source-of-truth rules table.
