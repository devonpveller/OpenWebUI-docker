# portal - the internet-facing front end

The only plane that faces the internet: Cloudflare Tunnel to Caddy to Authelia
to an app in the stack. Its own compose project (`portal`, named by the `-p
portal` every command passes; [`docker-compose.yml`](docker-compose.yml)).

**The driver will not start or stop it.** The plane is `manual` in
[`../stack.manifest.toml`](../stack.manifest.toml): exposing the stack to the
internet stays a deliberate human action, run through
[`portal-on.ps1`](../scripts/portal/portal-on.ps1) and
[`portal-off.ps1`](../scripts/portal/portal-off.ps1) on Windows, or the
equivalent `docker compose` lines below.

Commands below run from the repository root. The `.ps1` scripts need Windows
PowerShell; the `docker compose` and `python` lines run anywhere (use `python3`
if that is what your system calls Python 3.11+).

```
        internet                              tailnet (separate path)
           |                                          |
   [ cloudflared ]  edge-net   profile `internet`     |
           |                                          |
        [ caddy ] --- auth-net ---> [ authelia ]      |  caddy:8446
           |  app-net (ai-stack_app-net, external)    |  <----------
           v                                          |  (the frontend's
   openwebui:8080, open_notebook, openbrain-*         |   wiki route)
```

The tunnel is the `internet` profile, and `portal/.env` deliberately carries no
`COMPOSE_PROFILES` line: the profile is passed on the command line for each
production start, so exposure is never a standing setting.

| Service | What it is |
|---|---|
| `portal-init` | One-shot, no network. Chowns the volumes to the users the services run as; everything else waits for it to exit 0. |
| `caddy` | The reverse proxy and `forward_auth` client. Binds no host port. Config: [`config/caddy/Caddyfile`](config/caddy/Caddyfile). |
| `authelia` | Single sign-on and 2FA, on `auth-net` only. Its domains come from `PUBLIC_DOMAIN`. |
| `portal-alerter` | Receives alerts from the watchers and mails them through Gmail. |
| `authelia-watcher` | Tails the Authelia and Caddy logs and alerts on new source IPs, recording them in [`config/watcher/known-ips.txt`](config/watcher/known-ips.txt). |
| `authelia-notif-bridge` | Forwards Authelia's user notifications (2FA enrolment codes, password resets) to the alerter, so you receive them away from the machine. |
| `integrity-tripwire` | Hashes the Caddyfile and the Authelia configs on a schedule (`TRIPWIRE_CRON`) and alerts on drift. |
| `portal-cron` | Triggers the daily digest (`PORTAL_DIGEST_CRON`). |
| `caddy-backup`, `authelia-backup` | Nightly tars of `caddy-data` and `authelia-data` into `backups/caddy` and `backups/authelia`. |
| `cloudflared` | The tunnel - the only internet ingress. |
| `tunnel-watcher` | Probes `cloudflared` and alerts after three consecutive misses. |

## Requirements

- **Docker Engine with the compose plugin.** On Windows, PowerShell for the
  lifecycle scripts.
- **The frontend plane.** Caddy's main site proxies `openwebui:8080` over
  `ai-stack_app-net`, so Open WebUI must run under the frontend's `gpu` profile
  (the `stock` one is not on that network). The Open Notebook, wiki and
  workbench sites need the Open Brain plane, and `/ui` needs the inference
  plane's `llm-gateway-ui`; each of those sites answers 502 while its plane is
  off, and the rest of the portal serves.
- **A public domain and a Cloudflare tunnel** for it, with the tunnel's
  hostnames added in the Cloudflare dashboard.
- **A Gmail account the alerter can send from**, with its OAuth client at
  `secrets/google/portal-alerter/credentials.json` and a token at
  `secrets/google/portal-alerter/token.json` (the header of
  [`config/alerter/setup-token.ts`](config/alerter/setup-token.ts) creates the
  token). Without them the alerter runs but every send fails, and
  `portal-status.ps1` shows the error. `DIGEST_TO` must be set or it does not
  start at all.
- **An Authelia user database**: copy
  [`config/authelia/users_database.yml.template`](config/authelia/users_database.yml.template)
  to `config/authelia/users_database.yml` (gitignored) and follow its header to
  hash a password.

Keys, in `portal/.env`:

| Key | What happens if it is wrong |
|---|---|
| `CLOUDFLARE_TUNNEL_TOKEN`, `AUTHELIA_SESSION_SECRET`, `AUTHELIA_STORAGE_ENCRYPTION_KEY` | Blank: `portal-on.ps1` refuses before starting anything, and `stack.py enable --plane portal` / `doctor` refuse. |
| `AUTHELIA_JWT_SECRET` | Blank: as above, and the compose file itself refuses to render. Still the shipped `change-me-...`: `enable` and `doctor` refuse. |
| `PUBLIC_DOMAIN`, `ACME_EMAIL` | Still the shipped `ai.example.com` / `you@example.com`: `enable` and `doctor` refuse. |
| `DIGEST_TO`, `DIGEST_FROM` | Not checked by any script. The alerter crash-loops with `DIGEST_TO is required` while it is blank. |
| `WORKBENCH_KEY` | Not checked. Caddy sends it to Open Brain's workbench, and it must equal Open Brain's `MCP_ACCESS_KEY`; blank means every `/workbench` call is refused. |

`portal-on.ps1` reads its list of required keys from `[planes.portal] keys` in
the manifest, so the two cannot drift.

## Start and stop

On Windows:

```powershell
.\scripts\portal\portal-on.ps1 -WhatIf   # print every docker command, run nothing
.\scripts\portal\portal-on.ps1 -Test     # test mode: no tunnel, caddy on 127.0.0.1:8443
.\scripts\portal\portal-on.ps1           # production: --profile internet, publicly reachable
.\scripts\portal\portal-status.ps1       # read-only, one line per check
.\scripts\portal\portal-off.ps1          # stop, keeping volumes and config
```

`portal-on.ps1` refuses if `portal/.env` is missing or a required key is blank,
then starts the services in five ordered groups (alerter, Authelia, Caddy, the
watchers, the backups), adding a sixth - `cloudflared` and `tunnel-watcher` - in
production, and ends with `portal-status.ps1`.

By hand, anywhere:

```bash
docker compose -p portal -f portal/docker-compose.yml config --services
docker compose -p portal -f portal/docker-compose.yml -f portal/local-test.override.yml up -d
docker compose -p portal -f portal/docker-compose.yml --profile internet up -d
docker compose -p portal -f portal/docker-compose.yml --profile internet down
```

The second line is test mode, the third production, the fourth stops
everything and keeps the volumes. **Always pass `-p portal`**: the compose file
declares no `name:`, so without it the project is named after the directory and
you get a second, parallel set of volumes.

Test mode adds `127.0.0.1:8443` to Caddy through
[`local-test.override.yml`](local-test.override.yml) - there is no `local-test`
profile. A browser on `http://127.0.0.1:8443/` gets Caddy's catch-all `421`;
map your domain to `127.0.0.1` in your hosts file and visit
`http://<your domain>:8443/`. Cookies will not persist over plain HTTP, so test
mode checks routing and health, not the login flow.

## Operate

The driver knows this plane and declines to drive it:

| Command | What it does |
|---|---|
| `python scripts/stack/stack.py up portal` | starts nothing, and prints `# portal is not driven by stack.py - start it with scripts/portal/portal-on.ps1 / scripts/portal/portal-off.ps1` |
| `python scripts/stack/stack.py restart portal`, `recover portal` | refuse with the same pointer |
| `python scripts/stack/stack.py enable --plane portal` | checks the keys above, then records the plane; `up` still skips it |
| `python scripts/stack/stack.py backup portal` | archives the four named volumes (below) |

`stack.py health` has no portal probe; `portal-status.ps1` is what watches this
plane.

**Backup and restore.** The live state is two named volumes -
`portal_authelia-data` (users, 2FA devices, sessions) and `portal_caddy-data`
(certificates and the access log) - each tarred nightly by its backup sidecar.
`portal_caddy-config` is regenerated from the Caddyfile and
`portal_tripwire-data` holds the accepted hashes. On demand:

```bash
python scripts/stack/stack.py backup portal
docker compose -p portal -f portal/docker-compose.yml --profile internet down
python scripts/stack/stack.py restore portal --from backups/portal/manual-<UTC stamp>
```

`restore` refuses while a portal container holds a volume. Start the plane again
with `portal-on.ps1` or the `up -d` line above. The `config/` tree, the
`secrets/` files and `reports/portal-digest` are host files; back them up with
your own tools.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `portal-on.ps1` stops before starting anything, naming keys | They are blank in `portal/.env`. |
| `required variable AUTHELIA_JWT_SECRET is missing a value` | `portal/.env` is missing, or that key is blank. |
| `dependency failed to start: container portal-alerter is unhealthy` | `docker logs portal-alerter` - usually `DIGEST_TO is required (your own Gmail address).` |
| `authelia` restarting with `Errors occurred performing startup checks` | Authelia logs that line without its cause. First check that `config/authelia/users_database.yml` is a file: if a container started before you created it, Docker made an empty directory of that name. Remove the directory, create the file from the template, and start again. |
| `network ai-stack_app-net declared as external, but could not be found` | The anchor's networks are missing; `python scripts/stack/stack.py up` creates them. |
| The main site answers 502 | Open WebUI is not reachable on `ai-stack_app-net`: the frontend is down, or running under `stock`. |
| The tripwire alerts right after you edited the Caddyfile | Re-accept the baseline: `docker exec integrity-tripwire sh /scripts/tripwire.sh accept`. |
| After `portal-off.ps1`, `tunnel-watcher` and `authelia-notif-bridge` are still running | The script stops ten services by name and does not name those two. `docker compose -p portal -f portal/docker-compose.yml ps` shows what is left. |
| Changing `PUBLIC_DOMAIN` breaks login | Authelia validates its config against the domain: recreate it in the same sitting, `docker compose -p portal -f portal/docker-compose.yml up -d --no-deps authelia`. |

## Security notes

- **No host port in production.** All ingress arrives through `cloudflared`;
  test mode adds `127.0.0.1:8443` only.
- **`auth-net` is internal.** The portal's routes out are `edge-net` (the tunnel,
  and `caddy-backup`), `notify-net` (the alerter mailing Gmail, and
  `portal-cron`) and the project's `default` network (the two backups).
- **The hardening floor** is declared once at the top of the compose file
  (`x-hardening`, `x-hardening-ro`, `x-healthcheck-http`) and merged into each
  service: `cap_drop: ALL` and `no-new-privileges` everywhere, a read-only root
  filesystem everywhere except `portal-init`, and a non-root user everywhere
  except `portal-init` (which chowns) and `portal-cron`.
- **In an incident, use the killswitch, not `portal-off`.**
  [`breach-killswitch.ps1`](../scripts/portal/breach-killswitch.ps1) mails first,
  stops the exposed services, snapshots the Caddy and Authelia logs under
  `incident/<UTC stamp>/`, rotates the two Authelia secrets in `portal/.env`, and
  prints the recovery steps. `-DryRun` shows what it would do.
  [`access-query.ps1`](../scripts/portal/access-query.ps1) is the read-only
  "who reached the portal" review.
- **Exposing a new app is a recipe**, kept at the top of the Caddyfile beside the
  `(authelia_gate)` snippet: attach the backend to `ai-stack_app-net`, add the
  vhost, the hub card and the Cloudflare hostname, reload, and re-accept the
  tripwire baseline.
- **Pinned images.** The alerter, Authelia and Caddy images are pinned; bump them
  on purpose.

## Changing this plane

Adding, removing or moving a container is never a one-file change; the
checklist is
[`SERVICE-LIFECYCLE.md`](../documentation/runbooks/SERVICE-LIFECYCLE.md). The
places this plane appears:

- [`docker-compose.yml`](docker-compose.yml) and [`config/`](config). A new
  service MERGES the hardening blocks; a list written on a service REPLACES the
  anchored list, so one more `security_opt` or `cap_drop` entry means spelling
  out the whole list (extra capabilities go under `cap_add`).
- [`../stack.manifest.toml`](../stack.manifest.toml): `[planes.portal]`
  (including `manual` and the `keys` list `portal-on.ps1` reads), its `internet`
  profile, and the `portal` product.
- `scripts/portal/portal-on.ps1`, `portal-off.ps1` (its explicit service list),
  `portal-status.ps1`, `breach-killswitch.ps1`.
- `scripts/checks/check-project-configs.ps1` (it renders this file with
  `--profile internet`) and `scripts/backup/restore-from-snapshot.ps1` (the
  `caddy` and `authelia` entries).
- `.claude/skills/stack-map/references/workspace-stacks.md`,
  `documentation/CONTAINER-REGISTRY.md`, and the `portal` lease in
  `scripts/agent-harness/lease-names.conf`.

Not on that list, on purpose: `scripts/recovery/emergency-recovery.ps1` and the
driver's drive verbs do not manage this plane, and the generated inventory
`scripts/lib/stack-services.json` carries no portal rows - so a container added
here is invisible to the watchdog until someone adds it deliberately.

Then run `python scripts/stack/stack.py docs --check` and `/stack-map`.
