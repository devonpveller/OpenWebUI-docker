# search - the private search gateway

A web-search and page-fetch service for the rest of the stack whose traffic
leaves the machine only through a Mullvad WireGuard tunnel. One compose project
(`name: search`, [`docker-compose.yml`](docker-compose.yml)) of four services, no
profiles. What the gateway *application* does - endpoints, auth, providers - is
[`gateway/README.md`](gateway/README.md); this file is about running the plane.

Commands below run from the repository root. They are written `python`; use
`python3` if that is what your system calls Python 3.11+. Blocks marked `bash`
need a POSIX shell (Linux, macOS, or Git Bash on Windows).

| Service | What it is |
|---|---|
| `vpn` | gluetun holding a Mullvad WireGuard tunnel with a kill-switch, and an HTTP proxy on `:8888`. The plane's only route to the internet, used by SearXNG's engine queries and by Open Brain's page fetches. |
| `redis` | Cache for SearXNG (db 0, including engine suspensions) and for the gateway (db 1: responses and circuit-breaker state). Nothing is persisted. |
| `searxng` | The metasearch engine. Its configuration is [`searxng/settings.yml`](searxng/settings.yml), bind-mounted from this directory, which points every engine request at `http://vpn:8888`. |
| `gateway` | The front door, built here from [`gateway/`](gateway) as `private-search-gateway:local`: one API over the engines, with auth, caching and a circuit breaker. |

Order inside the plane: `searxng` waits for `vpn` and `redis` to be healthy,
and `gateway` waits for `searxng` to have started and `redis` to be healthy.

## Requirements

- **Docker Engine with the compose plugin, and Python 3.11+** for the driver.
- **`/dev/net/tun` and the `NET_ADMIN` capability** for gluetun. Docker Desktop
  and a normal Linux Docker Engine provide both.
- **A Mullvad account and one WireGuard key pair** from it: the private key and
  the address Mullvad assigns to that key.
- **No other plane.** It needs only the anchor's `ai-stack_default` network,
  which `up` creates. (A fresh clone does enable the frontend by default - see
  [Enable and start](#enable-and-start).)

Keys, in `search/.env`:

| Key | What happens if it is wrong |
|---|---|
| `MULLVAD_WG_PRIVATE_KEY` | Blank, or still the shipped `change-me-real-wg-private-key`: `enable`, `doctor` and `up` refuse. Any other invalid value gets past the driver and is refused by gluetun (see [Troubleshooting](#troubleshooting)). |
| `MULLVAD_WG_ADDRESSES` | Blank: `enable` and `doctor` refuse. IPv4 only, unless your Docker host has IPv6. |
| `GATEWAY_API_KEY` | Still the shipped `change-me-...`: `enable`, `doctor` and `up` refuse. The gateway's one required setting; host tools present it. |
| `SEARXNG_SECRET_KEY` | Still the shipped `change-me-...`: `enable`, `doctor` and `up` refuse. |
| `MULLVAD_COUNTRIES` | Exit country; `Netherlands` if unset. |
| `SEARCH_NET_SUBNET` | Opens gluetun's firewall to clients on other networks. The in-plane services never need it. |

## Enable and start

**On a fresh clone the frontend is already enabled.** With no
`.stack/state.json`, the driver treats the frontend as enabled, and `enable`
keeps it. So the `up` below starts the frontend first, and until
`frontend/.env` holds a real `WEBUI_SECRET_KEY` it stops there with
`# up stopped: frontend exited 1` and never reaches this plane. Either set up
the frontend as [its README](../frontend/README.md#enable-and-start) says, or run
this plane without it:

```bash
python scripts/stack/stack.py disable --plane frontend
```

```bash
cp search/.env.example search/.env
python -c "import secrets; print(secrets.token_hex(32))"
```

Fill in `MULLVAD_WG_PRIVATE_KEY` and `MULLVAD_WG_ADDRESSES` from your Mullvad
account, and a printed value each for `GATEWAY_API_KEY` and
`SEARXNG_SECRET_KEY`. Then:

```bash
python scripts/stack/stack.py enable --plane search
python scripts/stack/stack.py up
```

The first `up` builds `private-search-gateway:local` and pulls the other three
images. `searxng` starts only once `vpn` reports healthy, and its own
healthcheck allows 90 s for startup.

Is it up, and is it working? Two different questions:

```bash
curl -fsS http://127.0.0.1:8085/healthz
curl -fsS http://127.0.0.1:8085/readyz
```

`/healthz` answers whenever the gateway process serves. `/readyz` answers 503
until redis answers and at least one provider returns results.

## Operate

```bash
python scripts/stack/stack.py status
python scripts/stack/stack.py health
python scripts/stack/stack.py stats
python scripts/stack/stack.py recover search
python scripts/stack/stack.py down search
```

`health` runs two search probes: `/healthz`, and `/health`, which reports which
engines actually put results into recent answers. `unknown` (nothing searched
yet) passes; a measured `DEGRADED` fails.

`up -d` does not pick up a change under `gateway/`. Rebuild it on purpose:

```bash
docker compose -f search/docker-compose.yml build gateway
docker compose -f search/docker-compose.yml up -d gateway
```

**Backup and restore: there is nothing to back up.** The plane has no named
volume and no dump sidecar; `redis` is cache by design, and the configuration is
the tracked `searxng/` directory. `python scripts/stack/stack.py backup search`
refuses and says so.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `refused: search cannot be enabled yet:` naming a key | Set it in `search/.env`; nothing was changed. `python scripts/stack/stack.py doctor` lists every key still blank or at its shipped value. |
| `up` stops with `dependency failed to start: container search-vpn is unhealthy` | The tunnel did not come up. `docker logs search-vpn` says why. `private key is not valid: wgtypes: failed to parse base64-encoded key` means the key is not a WireGuard key at all. A well-formed key Mullvad does not know gives `restarting VPN because it failed to pass the healthcheck` with `i/o timeout` lines, over and over. Fix the key and address, then `python scripts/stack/stack.py up`. `python scripts/stack/stack.py down search` removes the containers the failed attempt left behind. |
| `network ai-stack_default declared as external, but could not be found` from a hand-typed `docker compose` | The anchor's networks are missing; `python scripts/stack/stack.py up` creates them. |
| `[DIFFERS]` on an `ai-stack_*` network, and `up` stops | An existing network does not match the anchor's declaration. The driver never alters one: stop what is attached, `docker network rm` it, run `up` again. |
| `/healthz` answers, `/readyz` is 503 | The chain behind the gateway: the tunnel still building, or redis or SearXNG unhappy. Nothing restarts on `/readyz`, so a plane that is up but not working stays that way until someone looks. |
| Fewer results than usual, without errors | Every query leaves through one exit IP, and a heavy fan-out can get it captcha'd. SearXNG keeps engine suspensions in redis db 0: `docker exec search-redis redis-cli -n 0 FLUSHDB`. |
| One engine returns nothing | Engine policy is in [`searxng/settings.yml`](searxng/settings.yml). |
| `git status` shows changes under `search/searxng/` you did not make | That directory is mounted read-write, and SearXNG writes into it. |
| Web search in Open WebUI fails | Open WebUI reaches `gateway` by name only under the frontend's `gpu` profile; under `stock` it cannot reach this plane at all. |

## Security notes

- **`search-net` is internal.** `redis` and `searxng` have no route out even if
  misconfigured; the only way out is the kill-switched `vpn`. That is what makes
  the privacy property structural rather than a matter of configuration.
- **`vpn` dials out on its own** - that is its job - so this plane reaches the
  internet as soon as it starts.
- **One published port, loopback:** `127.0.0.1:8085` for host tools, behind
  `GATEWAY_API_KEY`. The proxy on `vpn:8888`, SearXNG and redis publish nothing:
  an open forward proxy into a VPN, an unauthenticated SearXNG and an
  unauthenticated redis must not be reachable from the host or the LAN.
- **`vpn` and `gateway` are on the shared `ai-stack_default` network** so other
  planes can find them by name: Open WebUI (`SEARXNG_QUERY_URL`), and Open
  Brain's research and grounding services (`http://gateway:8080`,
  `http://vpn:8888`). Renaming either service breaks those consumers as a DNS
  failure.
- `docker compose -f search/docker-compose.yml config` prints the keys in plain
  text; do not paste its output.

## Changing this plane

Adding, removing or moving a container is never a one-file change; the
checklist is
[`SERVICE-LIFECYCLE.md`](../documentation/runbooks/SERVICE-LIFECYCLE.md). The
places this plane appears:

- [`docker-compose.yml`](docker-compose.yml), [`gateway/`](gateway/README.md) and
  [`searxng/`](searxng). The gateway receives exactly three variables
  (`GATEWAY_API_KEY`, `SEARXNG_URL`, `REDIS_URL`); its other settings run on
  their code defaults, and making one adjustable means adding it to the
  service's `environment:` block and to `search/.env.example` together.
- [`../stack.manifest.toml`](../stack.manifest.toml): `[planes.search]` and the
  `search` product.
- `scripts/stack/stack.py`: the two search probes in `HealthSweep.run()` and
  their labels in `PS1_PROBES` (`scripts/stack/test_stack.py`).
- `scripts/recovery/emergency-recovery.ps1` and
  `scripts/checks/stack-watchdog.ps1`.
- `scripts/lib/stack-services.curated.json`, then
  `python scripts/stack/stack.py inventory --write`.
- `.claude/skills/stack-map/references/workspace-stacks.md`,
  `documentation/CONTAINER-REGISTRY.md`, and the `search` lease in
  `scripts/agent-harness/lease-names.conf`.
- Image updates are manual, per
  [`UPDATE-MANAGEMENT.md`](../documentation/runbooks/UPDATE-MANAGEMENT.md).

Then run `python scripts/stack/stack.py docs --check` and `/stack-map`.
