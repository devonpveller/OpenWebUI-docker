# memory - the personal-memory layer

`mnemory`, a memory service that other planes read and write over MCP/REST, and
`mnemory-cloud-gateway`, the only door through which a cloud client may reach
it. One compose project (`name: memory`,
[`docker-compose.yml`](docker-compose.yml)) of three services, no profiles.

Commands below run from the repository root. They are written `python`; use
`python3` if that is what your system calls Python 3.11+. Blocks marked `bash`
need a POSIX shell (Linux, macOS, or Git Bash on Windows).

```
                        host loopback :8060
                               |
                     [ mnemory-cloud-gateway ]  <- the ONLY published door
                       memory_default + llm-net
                               |  http://mnemory:8050 (+ real key, X-User-Id)
   Open WebUI, Open Brain -->  [ mnemory ]  --------> http://llama-cpp:8080/v1
   (callers on llm-net)         llm-net only          (the inference plane)
                               |
                          memory_mnemory-data
                               |  :ro
                      [ mnemory-backup ] -> backups/mnemory
```

| Service | What it is |
|---|---|
| `mnemory` | The memory service, built from the sibling checkout `../mnemory` as `mnemory:local`. API on `:8050`, health on `:8051`. Stores to SQLite plus an embedded Qdrant under `/data`. Summarises and embeds through the inference plane's `llama-cpp` / `llama-cpp-embed` aliases. Authenticates callers with `MCP_API_KEY` (and any extra `MCP_API_KEYS`). |
| `mnemory-cloud-gateway` | A reverse proxy for cloud clients only, built from [`mnemory-gateway/`](mnemory-gateway). Default-deny: reads are filtered to memories labelled `share=cloud`, writes are stamped `origin=cloud, share=cloud`, caller-supplied `user_id`/`agent_id` are stripped, and every tool outside a small allow-list is blocked and hidden from `tools/list`. Cloud clients hold `MNEMORY_GATEWAY_KEY`; the gateway adds the real key and a fixed user upstream. |
| `mnemory-backup` | `alpine:3.21` loop that tars `/data` into `backups/mnemory` every `MNEMORY_BACKUP_INTERVAL` seconds (86400), keeping `BACKUP_RETAIN_COUNT` (2). It skips the run while the gateway is unreachable, and a skip exits 0. |

## Requirements

- **Docker Engine with the compose plugin, and Python 3.11+** for the driver.
- **The inference plane, enabled and serving.** `enable --plane memory` refuses while it
  is not enabled. mnemory reaches it only through the `llama-cpp` aliases, and
  needs its own virtual key there (below).
- **A mnemory checkout at `../mnemory`**, beside this repository - the build
  context of `mnemory:local`. `doctor` fails the plane and `enable --plane memory`
  refuses while that directory is missing or lacks `.git` or `Dockerfile`, and
  both print the command that creates it:

  ```bash
  git clone -b dev https://github.com/devonpveller/mnemory.git ../mnemory
  ```

Keys, in `memory/.env`:

| Key | What happens if it is wrong |
|---|---|
| `MCP_API_KEY` | Blank, or still the shipped `your-mnemory-api-key-here`: `enable`, `doctor` and `up` refuse. A hand-typed `docker compose` without it fails on the compose file's `${MCP_API_KEY:?}` guard. Trusted local callers present this key. |
| `MNEMORY_LLM_API_KEY` | Not checked. Blank means the compose default `mnemory`, which the gateway refuses with 401. Put a virtual key here ([issue one](../inference/README.md#issue-a-key-for-each-caller)). |
| `MNEMORY_GATEWAY_KEY`, `MNEMORY_CLOUD_USER`, `MCP_API_KEYS` | Not checked. A blank `MNEMORY_GATEWAY_KEY` gives a cloud door with an empty key rather than a refusal - set it before any cloud client uses port 8060. |

## Enable and start

**On a fresh clone the frontend is already enabled.** With no
`.stack/state.json`, the driver treats the frontend as enabled, and `enable`
keeps it. `up` starts the planes in dependency order - inference, then the
frontend, then this plane - so until `frontend/.env` holds a real
`WEBUI_SECRET_KEY`, the `up` below starts the inference plane (the
`llm-gateway*` containers), stops at the frontend with
`# up stopped: frontend exited 1`, and leaves those running with none of this
plane's containers started. Either give
the frontend its key - the `cp` and `WEBUI_SECRET_KEY` steps of
[its README](../frontend/README.md#enable-and-start); skip its `init`, which
refuses once `.stack/state.json` exists, and the frontend is enabled already -
or run this plane without it:

```bash
python scripts/stack/stack.py disable --plane frontend
```

(`python scripts/stack/stack.py enable --plane frontend` turns it back on
later; it refuses with `WEBUI_SECRET_KEY is missing in frontend/.env` until
that key is set.)

```bash
cp memory/.env.example memory/.env
python -c "import secrets; print(secrets.token_hex(32))"
```

Put the printed value in `MCP_API_KEY=`, and a virtual key from the inference
plane in `MNEMORY_LLM_API_KEY=`. Then:

```bash
python scripts/stack/stack.py enable --plane memory
python scripts/stack/stack.py up
```

The first `up` builds `mnemory:local` from `../mnemory` and
`mnemory-cloud-gateway` from this directory.

**A fresh build does not start today.** Built from the current `dev` branch of
`../mnemory`, `mnemory` crash-loops and `up` stops with
`dependency failed to start: container mnemory is unhealthy`. `docker logs
mnemory` shows two failures, one after the other:

1. `ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x`
   - the mnemory source declares `mcp>=1.6.0` with no upper bound, and the build
   resolves `mcp` 2.x. Changing it to `mcp>=1.6.0,<2` in
   `../mnemory/pyproject.toml` and running
   `docker compose -f memory/docker-compose.yml build mnemory` clears this one.
2. Then, on every start, a traceback through fastembed's
   `download_files_from_huggingface` ending in
   `httpx.ConnectError: [Errno -3] Temporary failure in name resolution`,
   `ERROR:    Application startup failed. Exiting.` and `SystemExit: 3`. On its
   first start mnemory asks Hugging Face for its BM25 sparse-embedding model,
   and `mnemory` cannot reach the internet: its only network,
   `ai-stack_llm-net`, is internal. It restarts and fails the same way each
   time.

The second one has no fix in this repository yet, so the plane cannot be brought
up from a fresh clone. **While memory is enabled, every plain `up` stops at it**
(`# up stopped: memory exited 1`), and the planes after it in the start order -
search, coder, Open Brain, agent-org - are never started. Take it back out and
stop the crash-looping container:

```bash
python scripts/stack/stack.py disable --plane memory
python scripts/stack/stack.py down memory
```

A machine that already has a working `mnemory:local` image runs the plane as
documented here: the compose file never pulls it (`pull_policy: never`), and a
plain `up` does not rebuild it.

## Operate

```bash
python scripts/stack/stack.py status
python scripts/stack/stack.py health
python scripts/stack/stack.py stats
python scripts/stack/stack.py recover memory
python scripts/stack/stack.py down memory
```

`health` probes the cloud door at `http://127.0.0.1:8060/health`. `mnemory`'s
own container healthcheck is on `:8051`; both dependants wait for it.

**Backup and restore.** `mnemory-backup` writes a nightly tar of
`memory_mnemory-data` into `backups/mnemory`. On demand:

```bash
python scripts/stack/stack.py backup memory
python scripts/stack/stack.py down memory
python scripts/stack/stack.py restore memory --from backups/memory/manual-<UTC stamp>
python scripts/stack/stack.py up
```

`backup` tars the volume even while `mnemory` runs and records that it was a
live copy; stop the plane first if you want a quiescent one. `restore` verifies
every checksum first and refuses while a container holds the volume.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `refused: memory requires inference, which is not enabled` | Enable the inference plane first: `python scripts/stack/stack.py enable --plane inference`. |
| `../mnemory is missing (plane memory)` from `enable` or `doctor` | Run the `git clone` it names, from the repository root. |
| `unable to prepare context: path ".../mnemory" not found` from `up memory` | `up <plane>` does not check the sibling checkout; `enable` and `doctor` do. Clone it. |
| `dependency failed to start: container mnemory is unhealthy`, and later planes never start | See [the fresh-build note](#enable-and-start); read `docker logs mnemory`. `python scripts/stack/stack.py disable --plane memory` lets `up` reach the rest. |
| 401 in `docker logs mnemory` when it summarises or embeds | `MNEMORY_LLM_API_KEY` is not a virtual key the gateway issued. |
| `network ai-stack_llm-net declared as external, but could not be found` from a hand-typed `docker compose` | The anchor's networks are missing; `python scripts/stack/stack.py up` creates them. |
| `[DIFFERS] ai-stack_llm-net: internal is false, declared true` and `up` stops | An existing network does not match the anchor. Stop what is attached, `docker network rm ai-stack_llm-net`, run `up` again. |
| No new file in `backups/mnemory`, and `mnemory-backup` exits 0 | The sidecar skips while `mnemory-cloud-gateway:8060` is unreachable, and a skip is exit 0. Check the newest file's age, not the exit code. |
| A restore "worked" and nothing changed | Restore into the volume `mnemory` actually mounts: `docker inspect mnemory --format "{{range .Mounts}}{{.Name}}{{end}}"`. The sibling repository's own compose file creates a similarly named `mnemory_mnemory-data`. |

## Security notes

- **Two doors.** Callers on `ai-stack_llm-net` (Open WebUI's mnemory tool and
  filter, Open Brain) talk to `mnemory:8050` directly with `MCP_API_KEY` and see
  everything. Cloud clients get `127.0.0.1:8060` and only what the gateway's
  policy allows. Do not publish a port on `mnemory`, and treat any widening of
  the gateway's allow-list as a privacy change.
- **`mnemory` has no internet.** Its only network is `ai-stack_llm-net`, which
  is internal. A feature that needs outbound HTTP has to be redesigned, not
  configured.
- The only published port is `127.0.0.1:8060`, loopback.
- The gateway holds the real mnemory key; a cloud client must never be given
  `MCP_API_KEY`.

## Changing this plane

Adding, removing or moving a container is never a one-file change; the
checklist is
[`SERVICE-LIFECYCLE.md`](../documentation/runbooks/SERVICE-LIFECYCLE.md). The
places this plane appears:

- [`docker-compose.yml`](docker-compose.yml) (with its `x-hardening` block,
  merged with `<<:`; a list written on a service REPLACES the anchored list) and
  [`mnemory-gateway/`](mnemory-gateway).
- The compose healthcheck probes `:8051` (`MGMT_PORT`), overriding the image's
  `:8050` one: change them together. `mnemory-backup`'s `HEALTH_TCP` must be
  `mnemory-cloud-gateway:8060`.
- [`../stack.manifest.toml`](../stack.manifest.toml): `[planes.memory]`,
  including its `host_paths` entry for `../mnemory`, and the `memory` product.
- `scripts/stack/stack.py`: the memory probe in `HealthSweep.run()` and its label
  in `PS1_PROBES` (`scripts/stack/test_stack.py`).
- `scripts/recovery/emergency-recovery.ps1` and
  `scripts/checks/stack-watchdog.ps1` (which restarts `mnemory` and
  `mnemory-backup` and alerts when `backups/mnemory` has nothing newer than
  52 h).
- `scripts/lib/stack-services.curated.json`, then
  `python scripts/stack/stack.py inventory --write`.
- `.claude/skills/stack-map/references/workspace-stacks.md`,
  `documentation/CONTAINER-REGISTRY.md`,
  [`restore-from-snapshot.md`](../documentation/runbooks/restore-from-snapshot.md),
  [`backup-restore-runbook.md`](../documentation/runbooks/backup-restore-runbook.md),
  and the `memory` lease in `scripts/agent-harness/lease-names.conf`.

Then run `python scripts/stack/stack.py docs --check` and `/stack-map`.
